# The public catalogue

How the shop window is generated, how to rebuild it, how bundle pricing is
configured, and how to look at it safely before anyone else does.

The measure this was built against: a buyer who has never heard of us lands
here from a Facebook Marketplace link, browses confidently on their phone,
adds three things they want, and sends one enquiry — and everything needed to
reply comes through.

---

## 1. What the site is

A folder of static files. No framework, no build step, no server, no
database, no cookies, no analytics, and nothing loaded from any other
company. Every page is complete HTML the moment it is written.

```
estate/site/
  index.html                  everything, with search / sort / filters
  category/<slug>.html        one page per category that has items in it
  items/<ITEM_ID>.html        one page per item
  bundle.html                 the basket, and one enquiry for the lot
  about.html                  how the sale works, and the general contact form
  photos/<ITEM_ID>/*.jpg      EXIF-stripped web derivatives only
  catalog.json                public feed (no internal status vocabulary)
  catalog_manifest.json       id -> {status, sold, price, band}
  bundle_config.json          the tier table this build was generated with
  sitemap.xml                 written only when ESTATE_CATALOG_URL is set
  robots.txt
  api/inquiry.py              the standalone serverless inquiry function
  api/_lib/                   verbatim copies of the real validation modules
```

Generated by `src/estate/site.py`. The inquiry function is
emitted by `estate/serverless.py`, which copies `inquiry_validation.py` and
`inquiry_notifier.py` into the build rather than reimplementing them, so the
deployed code and the tested code are the same code.

### Rendering policy: server-side, always

Every card and item page is real HTML in the file. JavaScript filters, sorts
and manages the basket by showing and hiding elements that are **already in
the document**. It never builds markup from item data.

This is a correctness rule before it is a performance one. The previous
generator embedded the catalogue as JSON inside a `<script>` tag and rebuilt
the grid with `innerHTML`. Item text originates from a vision model reading
whatever is printed on a photographed object — untrusted content, per
`CLAUDE.md` — and an item named `Chair </script><script>…` closed the element
and executed. That was real and reproducible. Rendering through `e()` removes
the class of bug, and means the catalogue still works with JavaScript off,
blocked, or still loading.

If you add anything to this generator: item text goes through `e()`, and the
only things that may appear inside a `<script>` element are numbers and item
IDs, via `_json_for_html()`.

## 2. Rebuilding it

```bash
python scripts/estate_site.py                    # -> estate/site
python scripts/estate_site.py --out /var/www/cat # -> anywhere
```

On a VPS:

```bash
cd /opt/listing-forge
sudo -u listingforge .venv/bin/python scripts/estate_site.py --out estate/site
```

The build is idempotent and safe to re-run. It rewrites every page, deletes
item and category pages that are no longer publishable, and regenerates the
photo directory from scratch.

### In the sandbox

SQLite cannot take file locks on the mounted repo path — you get
`disk I/O error`. Point `DATABASE_URL` somewhere outside the mount:

```bash
cp data/database/agent.db ~/work/agent.db
DATABASE_URL="sqlite:///$HOME/work/agent.db" \
ESTATE_INVENTORY_DIR="$HOME/work/inventory" \
PYTHONPATH=src python scripts/estate_site.py --out ~/work/site
```

### Environment it reads

| Variable | Effect if missing |
|---|---|
| `ESTATE_CATALOG_URL` | **Share previews break.** No absolute OpenGraph URLs and no sitemap, so a link pasted into Facebook or a text message shows a bare address instead of the photograph and price. The build warns. |
| `ESTATE_SELLING_EMAIL` | A buyer whose enquiry fails to send gets no fallback route. The build warns. |
| `ESTATE_BRAND_NAME` | Falls back to "The Collection". |
| `ESTATE_PICKUP_REGION` | Location is simply not shown. The address is never shown either way. |

### Reading the output

```
Built 12 item(s) in 4 categor(y/ies), 58 photo(s) -> /opt/.../estate/site

3 approved item(s) held back from the catalogue:
  DK-202608-014
      - Defects field is empty. Record what was found — 'None observed on
        inspection' is a disclosure; blank is not.
```

That block is the one to read. An item a human already approved that is
silently missing from the site is the most confusing state this system can
produce, so every held-back item is named with the exact gate holding it.

## 3. What is allowed to be published

`site.publication_blockers()` is the last gate before the outside world. An
item appears only when **all** of these hold:

1. Ownership confirmed (`ownership_approval`).
2. No `[MOCK]` marker anywhere in any published field — not just the start of
   the name.
3. Identification reviewed (`review_status == "Reviewed"`).
4. At least one confirmed comparable: has a URL, is not a placeholder, and is
   not awaiting confirmation. No placeholder comparables attached at all.
5. Pricing approved by a human: both `current_price` and `floor_price` set,
   and `approval_status == "Approved"`.
6. Defects disclosed — `defects` is non-empty, and condition is not Unknown.
7. At least one photograph.
8. Website copy complete: title, description and condition statement.
9. Availability public: `website_status` in Queued / Published / Sold (shown),
   and `status` in `PUBLISHABLE_STATUSES`.

This deliberately re-checks conditions that `approval.prepare_review` also
checks. Approval can be bypassed — `estate/demo.py` does exactly that, on
purpose — and `website_status` can be set by a direct repository update.
Checking again here means neither route puts an unfinished item in front of a
buyer.

**On the defects gate.** A blank `defects` field means nobody wrote anything,
not that nothing is wrong; the field note in `schema.py` has always said so.
"None observed on inspection" is a disclosure. Blank is not. This is the gate
most likely to hold an item back, and it is working as intended.

None of these may be relaxed to make a build produce more items.

## 4. Bundle pricing

### Where it is configured

`estate/config/pricing.json`, under `bundle`. Read at build time; change it
and rebuild, no code change and no deploy of the generator.

```json
"bundle": {
  "enabled": true,
  "max_items": 25,
  "round_to": 5,
  "tiers": [
    {"min_items": 2, "discount_pct": 0.05},
    {"min_items": 3, "discount_pct": 0.10},
    {"min_items": 5, "discount_pct": 0.15}
  ]
}
```

Tiers must ascend by `min_items`. Malformed rows are dropped rather than
clamped: a nonsensical tier is a configuration mistake, and quietly
reinterpreting it as some other discount would hide the mistake behind a
number that looks deliberate. A missing or unreadable `bundle` section falls
back to the values above.

The table travels with the build as `bundle_config.json`, so the browser, the
inquiry function and the private side all use the same one.

### The floor rule, and why bands exist

**A bundle discount may never take any selected item below its approved
`floor_price`.** That is a human-approved number and nothing automated
undercuts it.

The obvious implementation is wrong. Publishing each item's maximum
permissible discount so the browser can find the binding constraint is
algebraically identical to publishing its floor:

```
max_discount = 1 - floor / price      ->      floor = price × (1 - max_discount)
```

A buyer with a calculator would read every floor off the page.

So each item publishes a **band** instead: the index of the deepest
configured tier it can absorb without breaching its floor. With three tiers a
band is 0–3 — about two bits. It says "this piece can bear at least 10%" and
nothing more.

The discount applied to a basket is:

```
min( tier for the number of items , the lowest band in the basket )
```

which is the binding constraint across the selection.

**Why the floor holds.** Item *i* has price `p_i`, floor `f_i`, headroom
`h_i = 1 - f_i/p_i`. Its band is chosen so `tier[band_i] ≤ h_i`. The applied
discount `d ≤ tier[band_i] ≤ h_i` for every selected item, so the effective
price `p_i × (1 - d) ≥ p_i × (f_i / p_i) = f_i`. Item by item, and therefore
for the total.

`tests/unit/test_estate_bundling.py` throws several hundred floor-constrained
baskets at this and asserts the invariant on every item of every one.

### Where the code lives

| File | Role |
|---|---|
| `estate/bundling.py` | Private side. Reads the config, computes each item's band from its price and floor. Never shipped to the site. |
| `estate/inquiry_validation.py` | The arithmetic: `normalise_tiers`, `tier_discount_for_count`, `bundle_quote`, `parse_basket`, `validate_bundle`, `manifest_entries`. Copied verbatim into the public bundle, so it stays import-free. |
| `estate/site.py` | Bakes the price/band table and the tier table into the page as numbers. |

One implementation of the maths means the number a buyer saw, the number
recomputed when their enquiry lands, and the number that reaches Telegram
cannot disagree.

### What a buyer sees

Selection persists in `sessionStorage` (guarded — some privacy modes throw
rather than return null, so the in-memory copy is the source of truth and it
degrades to per-page rather than breaking). A `?b=ID1,ID2` link is merged in
once on load, so a selection can be shared or come back to.

The total is labelled indicative everywhere it appears, and the page says a
person confirms on reply. **The website never commits to a price.**

If an item in the basket is near its floor, the page says so in plain words
rather than silently quoting a smaller percentage.

### Tuning it

Raising a tier is safe: floor-constrained items cap themselves. Lowering
`round_to` to 0 disables rounding. Setting `enabled` to false leaves the tier
table empty, which quotes no discount at all — the fail-closed direction.

After any change: rebuild, then check `bundle_config.json` in the output.

## 5. Enquiries

Three routes, one endpoint (`api/inquiry`, same-origin and relative — never
the private VPS API):

- **Per item** — the form on an item page, carrying `item_id`.
- **Bundle** — the form on `bundle.html`, carrying `items`.
- **General** — the form on `about.html`, with an optional reference.

Every protection is unchanged: honeypot, format validation, normalisation,
manifest validation, availability checks, duplicate suppression, salted and
truncated IP hashing, best-effort rate limiting, generic error bodies, and
**durable-only success** — 200 only when something durable happened, 503
otherwise. A buyer is never thanked for a message nobody will read.

A basket is untrusted input. Only well-formed IDs survive parsing, every
survivor is validated against the manifest, and the quote is computed from
the manifest's prices and bands — never from the request body. A payload
claiming its own total is ignored.

An unavailable item fails the whole basket with a 409 and names it. Quietly
selling three of the four things someone asked for, without saying which one
went, is the small dishonesty that loses a buyer at the worst possible
moment.

The Telegram message carries every item and its individual price, the
subtotal, the discount applied, the indicative total, and a note when the
discount was capped by an item near its floor — so a reply can be written on
a phone without opening a laptop.

Delivery needs `ESTATE_INQUIRY_TELEGRAM_BOT_TOKEN` and
`ESTATE_INQUIRY_TELEGRAM_CHAT_ID` in the deployment environment. Use a
**dedicated bot**, not the main D.R.A.K.E. token: a public function is a
wider trust boundary, and a leak there must not hand anyone control of the
bot that reads Drake's own messages.

## 6. Previewing it safely

### Locally, with real inventory

```bash
python scripts/estate_site.py --out /tmp/preview
python -m http.server 8080 --directory /tmp/preview
```

Open `http://localhost:8080`. Everything works except the enquiry form, which
needs the serverless runtime.

### Locally, with sample data

```bash
python scripts/estate_demo.py --fresh --out /tmp/demo
```

This is a **preview build**: publication gates are relaxed so sample items
can exercise the catalogue, every page carries a visible preview banner, and
`robots.txt` is `Disallow: /`. The build report's first warning says not to
deploy it. Never do.

### As a password-protected deployment

```bash
cd estate/site
vercel                      # preview URL, NOT --prod
```

Then set a deployment password in the Vercel project settings before sharing
the URL.

**`vercel --prod` is Drake's decision and nobody else's.** Do not run it.

Deploy only `estate/site/` — never the repository root, which contains the
database, `.env`, and the whole private system.

## 7. Never leaking

`tests/integration/test_estate_site_leaks.py` builds a site from an item
deliberately loaded with every private value the system holds, then reads
every byte of every output file and fails on any of:

`floor_price` as a label or a value, internal and private notes, the physical
address, priority scores and reasons, comparable source URLs, research
worksheets, `/estate/` private routes, the VPS host and port,
`ESTATE_REVIEW_TOKEN` / `review_token`, anything matching `bot<digits>:`, and
**every value of length ≥ 8 in the repository's real `.env`**.

That last check is the one that catches a secret nobody thought to list. It
reads the actual file rather than a fixture, and never prints a matched
value.

The same module asserts the things that *should* be public are — a leak test
that would also pass on a blank page proves nothing.

Run it before any deploy:

```bash
python -m pytest tests/integration/test_estate_site_leaks.py -q
```

## 8. Tests

```bash
python -m pytest tests/unit/test_estate_bundling.py \
                 tests/integration/test_estate_catalogue.py \
                 tests/integration/test_estate_site_leaks.py \
                 tests/integration/test_estate_site_inquiry_decoupling.py \
                 tests/integration/test_estate_inquiry_endpoint.py -q
```

| File | Covers |
|---|---|
| `test_estate_bundling.py` | Tier table, bands, floor enforcement under bundling, basket parsing and validation |
| `test_estate_catalogue.py` | Publication gates one by one, categories, search and sort attributes, sold-item handling, image order, share-preview tags, empty catalogue, the XSS regression |
| `test_estate_site_leaks.py` | The whole-site scan |
| `test_estate_site_inquiry_decoupling.py` | The build emits the function and the manifest, and points nowhere near the private API |
| `test_estate_inquiry_endpoint.py` | Executes the **emitted** `api/inquiry.py` — the exact source deployed — including the bundle path |

When testing default settings, isolate from the production `.env` with
`Settings(_env_file=None)`. There is an AST guard in
`tests/unit/test_config.py` that fails the build if you forget; a bare
`Settings()` once printed a live bot token into a terminal and the token had
to be revoked.
